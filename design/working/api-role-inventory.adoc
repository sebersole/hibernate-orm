The first four groups give 1,793 extension-review shapes, of which 256 are
currently incubating. Of those 1,793, 1,575 belong to artifacts selected for
migration enforcement; 1,319 are both in that scope and not incubating.

These are structural counts, not promises of supported extension. Public and
protected accessibility is examined along with enclosing types and constructor
access. Sealed types are not blindly classified as externally implementable.
The other 465 types are outside this initial ordinary-extension review;
in particular, annotation implementations have special semantics and are not
claimed to be Java-impossible merely because annotation types are set aside.

The apparent workload is inflated by 377 extensible types in generated grammar
packages. Many function implementations, Envers boot-model classes, and other
implementation-oriented classes also currently resolve to API. Those deserve
a category-intent review before deciding that their Java extensibility is a
supported application contract. This report does not reclassify them.

== Automatic evidence triage

The first pass divides the 1,793 extension-review shapes as follows:

[cols="3,1",options="header"]
|===
|Direct evidence found |Types
|Tests, test infrastructure, or another ORM module |81
|Standalone provider-fixture context |1
|Only the owning module's implementation or benchmarks |499
|No direct implementation evidence located |1,212
|===

The 82 types with evidence outside the owner's ordinary implementation are a
priority review queue, not 82 approved extension contracts. Indirect subtype
and override-signature evidence is retained separately. Source and bytecode
observations are labeled and may describe the same relationship; do not sum
raw evidence rows as independent implementations.

Owning-module implementations are deliberately distinguished from cross-module
use. For example, Envers implementing its own `AuditReader` is not stronger
evidence of supported application implementation than Core implementing
`Session`. Runtime mocks and proxies are not statically generated classes in
the scan; concrete test doubles are evidence only, not contract approval.

== Preliminary role recommendations

Source documentation and representative tests support 21 high-confidence
recommendations for `USE + IMPLEMENT`, assuming their existing API category
is retained. Fourteen are non-incubating; seven are currently incubating.

[cols="2,4",options="header"]
|===
|Family |Types
|JDBC work callbacks and bases
|`Work`, `ReturningWork`, `AbstractWork`, `AbstractReturningWork`
|Application callbacks
|`Interceptor`, `EntityNameResolver`, `CustomEntityDirtinessStrategy`,
`CustomEntityDirtinessStrategy.AttributeChecker`, `SessionFactoryObserver`
|Naming strategies
|`ImplicitNamingStrategy`, `PhysicalNamingStrategy`
|Result transformation
|`TupleTransformer`, `ResultListTransformer`
|Criteria construction
|`CriteriaDefinition`
|Envers callbacks
|`RevisionListener`, `EntityTrackingRevisionListener`
|Value/identifier generation
|`BeforeExecutionGenerator`, `OnExecutionGenerator`, `IdentifierGenerator`
|Custom annotation binding
|`TypeBinder`, `AttributeBinder`
|===

The generated recommendations report gives the exact declaration, lifecycle,
documentation evidence, and representative test locations for each type.
This is a deliberately bounded manually reviewed shortlist, not a claim
that other API types lack implementation contracts.

`ImplicitNamingStrategy` illustrates why documentation matters: its Javadoc
explicitly anticipates application implementations, even though many tests
extend its standard implementation rather than implementing the interface
directly. That adds an important recommendation beyond the direct-evidence
queue.

`CriteriaDefinition` is particularly useful for designing API roles. Its
documented usage is an anonymous subclass with an initializer block; supported
subclassing does not require the application to override an abstract method.
TYPE-level implementation intent must protect this usage too.

Eight additional types are reasonable candidates to review for explicitly
use-only intent: `Session`, `StatelessSession`, `SessionFactory`, `Query`,
`SelectionQuery`, `MutationQuery`, `Metadata`, and `MetadataBuilder`.
They remain unreviewed. Third-party wrappers and delegators must be considered;
neither their facade shape nor the absence of repository implementations is
proof that implementation has never been supported.

== Counterexamples and design implications

=== Tests are not automatically extension contracts

The provider-fixture evidence for `SqlStringGenerationContext` is
`ExampleSchemaExporterTest.FixtureContext`. This is a test context supplied
to an exporter test, not by itself proof of a supported application extension
point. `GeneratorCreationContext` likewise has unit-test and test-infrastructure
implementations which require interpretation. Neither is on the high-confidence
shortlist.

`HibernateCriteriaBuilder` has a real cross-module subtype in Spatial. This
establishes an in-repository dependency and may indicate a supported extension
surface, but does not alone resolve what arbitrary external applications may
implement. It remains a separate contract-review candidate.

=== Member classifications must remain independent

159 API types have directly declared methods, fields, or constructors whose
effective category differs from the enclosing API type. Of these, 150 are
in the extension-review shapes. This count includes many community Dialects;
it is not 150 demonstrated needs for member-level API-role annotations.

For example, `CustomEntityDirtinessStrategy` is an API type with documented
application implementation, but four callback methods are individually SPI
classified. An API type's role must not overwrite these categories, nor may
the presence of SPI-classified callbacks make the documented implementation
obligations disappear. Constructors and inherited obligations need similarly
explicit treatment in the future working specification.

TYPE-only API role declarations still look viable. The evidence does not
justify adding member-level API-role annotations now. It does establish that
role propagation cannot simply replace every member's independent category
or existing SPI roles with those of the enclosing type.

=== Lifecycle and category are separate decisions

Seven of the 21 strongest implementation candidates are incubating. They still
have recognizable implementation intent, even though they do not carry the
stable compatibility guarantee. Do not omit their role inventory or promote
their lifecycle status as part of adopting roles.

Likewise, being API-classified today does not settle whether a generator or
bootstrap extension would ultimately be better classified as SPI. This
inventory records the current category and participation evidence; a category
change is a separate, compatibility-sensitive decision.

== Method and coverage limitations

. Regenerated canonical classification metadata using the existing Gradle task.
. Parsed 18,417 tracked Java files using the JDK compiler's parse-only API:
  30,518 named, local, and anonymous class declarations. Annotation processors
  and Java code were not executed.
. Scanned 44,497 existing compiled classes across ORM subprojects using ASM,
  collecting hierarchy, member signatures, sealed/inner-class structure, and
  LambdaMetafactory sites for lambda and method-reference implementation evidence.
. Resolved source parents against canonical and repository type names using
  explicit imports, package/enclosing scope, and unambiguous wildcard imports.
. Checked public/protected constructor access and collected direct, indirect,
  and override-signature observations; reviewed representative documentation
  and tests before making the 21 strong recommendations.

Six documentation Java snippets had parse errors because they are fragments,
not complete compilation units. There were 2,491 unresolved source-parent
references, including external-library types absent from the inventory.
The source pass is parse-only, not a complete javac symbol analysis. Static
imports of nested types and some local/generated constructs can remain
unresolved. Javadoc and AsciiDoc examples were inspected selectively, not
parsed exhaustively as Java programs.

Only 30,560 scanned class files could be associated with a unique current
source file and a current named declaration or anonymous/local class shape.
13,937 were excluded from supplementary bytecode evidence because source was
missing, ambiguous, or the named declaration no longer existed. The scan
encountered 655 uniquely source-associated classes with newer source than
bytecode; included observations carry a freshness warning. These counts do
not claim that the cached tests were freshly rebuilt for this inventory.

Anonymous/local binary names cannot be matched completely without fresh
compilation. Bytecode evidence and matching override signatures are therefore
supplementary observations, not proof of a current compiled consumer or a
complete Java overriding analysis. No test suite was executed. Repository
evidence cannot establish the absence of implementations in external code.

== Recommended next step

Use the 21 strong recommendations and representative ambiguous cases as
fixtures for the future TYPE-only API-role specification. Review the remaining
evidence queue by feature family, with category and lifecycle decisions kept
separate. Do not require completion of all 1,793 extension-review shapes before
delivering consumer classification reporting.

No unreviewed declaration should become use-only automatically. Approved
decisions eventually belong in source and contract documentation; this
temporary report can then be discarded rather than maintained as a ledger.
